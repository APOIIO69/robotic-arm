# Заметка 5: Инфраструктура, сборка и оркестрация

## 5.1. Специфика сборки библиотек micro-ROS
Для работы C-контроллера на хосте требовалось собрать клиентские библиотеки micro-ROS.

**Технический нюанс (флаг --merge-install):**
Стандартная сборка ROS 2 (`colcon build`) создает изолированные папки для каждого из сотен пакетов (`install/rcl/...`, `install/rmw/...`). Для классического C-проекта это превращает настройку `Makefile` в кошмар, так как нужно прописать сотни путей `include`.

**Решение:**
Мы использовали флаг `--merge-install`. 
*   **Как это работает:** Все заголовочные файлы из всех пакетов ROS 2 копируются в одну общую директорию `install/include`, а все библиотеки — в `install/lib`.
*   **Результат:** Наш `Makefile` стал лаконичным и надежным, ссылаясь всего на пару системных путей.

## 5.2. Управление Middleware (RMW Implementation)
По умолчанию ROS 2 на Ubuntu пытается использовать протокол DDS (например, CycloneDDS или FastDDS). Наш же контроллер говорит на языке XRCE-DDS (через micro-ROS Agent).

**Решение:**
В скрипте запуска мы явно устанавливаем переменную окружения:
`export RMW_IMPLEMENTATION=rmw_microxrcedds`
Это заставляет систему использовать специфическую реализацию middleware, которая умеет транслировать стандартные сообщения ROS 2 в компактный формат micro-ROS.

## 5.3. Оркестратор run_system.py
Поскольку проект состоит из множества независимых компонентов, их ручной запуск в правильной последовательности отнимал много времени.

**Логика работы оркестратора:**
1.  **Последовательный запуск:** 
    *   Агент (слушает порт).
    *   Webots (загружает мир).
    *   C-контроллер (подключается к Webots и Агенту).
    *   PID-нода (обрабатывает математику).
    *   Backend (выставляет API наружу).
2.  **Групповое управление (Process Groups):** Скрипт использует `os.setsid()` при запуске подпроцессов. Это создает новую сессию для каждого процесса. 
3.  **Безопасное выключение:** При нажатии `Ctrl+C` оркестратор вызывает `os.killpg()`. Это гарантирует, что сигнал завершения получат не только "родители", но и все их "дети" (например, если Python-скрипт запустил внутри себя bash-оболочку). Это предотвращает утечки памяти и занятые порты.

## 5.4. Решение проблемы с типами данных (Typesupport)
Мы столкнулись с ошибкой "Type support not from this implementation". Это происходило потому, что стандартный `rcl` пытался использовать универсальные дескрипторы типов, которые не понимал `rmw_microxrcedds`.

**Решение:**
В коде C-контроллера мы перешли на использование макроса `ROSIDL_TYPESUPPORT_INTERFACE__MESSAGE_SYMBOL_NAME`. Это позволило на этапе компиляции жестко связать сообщения с реализацией `microxrcedds_c`, исключив динамическое определение типа, которое давало сбой.
